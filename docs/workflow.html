ビルドが要るか

右側（セントラル）は ZMK Studio が有効です（CONFIG_ZMK_STUDIO=y、ロック無し）。キー割り当ての正本は ZMK Studio です。割り当てを変えるときは zmk.studio に USB でつなぎ、Studio で変えて保存します。ビルドも書き込みも要りません。

変えたいもの手段触るファイル
キー割り当て、レイヤーの使い分けビルド不要 ZMK Studio（正本）—
コンボ、エンコーダの割り当て（sensor-bindings）、新しい behavior要ビルドconfig/sosho.keymap
スクロール量などのマクロ（#define）要ビルドconfig/sosho.keymap
ポインタの速度・反転・スクロール化（input-processors）要ビルドboards/shields/sosho/*.overlay
Bluetooth・LED・電池などの設定（Kconfig）要ビルドboards/shields/sosho/*.conf
このリポジトリ独自のコード（src/・Kconfig・CMakeLists.txt。充電表示など）要ビルドsrc/
ピン配置などのハードウェア定義、外部モジュール要ビルド*.dtsi・config/west.yml

予約レイヤー: キーマップ末尾の scroll と extra2 は status = "reserved" の空き枠です。Studio からレイヤーを増やすときに使われるので、Studio で使うだけなら再ビルドは要りません。

キーマップのファイルとの関係: config/sosho.keymap の割り当て（各レイヤーの bindings）は初期値です。Studio で保存すると、その内容がキーボード本体に記録されてファイルより優先され、以後ファイルの割り当てを書き換えて書き込んでも反映されません（ZMK 公式ドキュメントの記述による）。

  • そのため、資料のレイヤー図（ファイルから作る）は初期値を示します。実機のいまの割り当ては Studio で見ます。
  • ファイルの初期値に戻したいときは、Studio の「Restore Stock Settings」を実行します（Studio での変更は消えます）。
  • コンボ、behavior の定義、ポインタ、Kconfig など、Studio で扱えないものは引き続きファイルで管理します。

開発の流れ

ファイルを編集してビルドする変更は、次の順で進めます。

  1. ブランチを切る。 main から作業用のブランチを作ります。名前の付け方は ブランチ を参照。

    git switch -c feature/<名前> main

  2. 編集する。 どのファイルを触ると何が変わるかは 設定項目 › どこを触ると何が変わるか にあります。触るファイルが 既知の課題 に載っていないかも確かめます。

  3. lint を通す。 ツールチェーン無しで 1 秒かからず終わります。ok: が出るまで直します。キーの数や括弧の対応に加えて、使っているラベル（&kp や &zip_* など）が ZMK に実在するかも確かめ、見つからなければ警告を出します。

    python3 scripts/lint-keymap.py

  4. 資料を作り直す。 設定の変更が資料の自動生成部分に反映されます。

    python3 scripts/gen-docs.py

  5. ビルドする。 普段は 1 ターゲットだけ。キーマップの変更なら約 14 秒です。

    ./scripts/build-local.sh sosho_R_trackpad

  6. 書き込んで、実機で確かめる。 どちらの半分に書き込むかは 書き込み を参照。

  7. コミットする。 メッセージは日本語で書きます。

  8. main に取り込み、タグを打つ。 実機で問題がなければ取り込みます。手順は 取り込みとタグ を参照。

git の運用

リモート

  • origin は自分の GitHub フォーク（amaeno/unified-zmk-config-template）です。バックアップ置き場として使います。
  • フォーク元（upstream）はリモートに登録しません。追従しないので不要で、あると誤って fetch や push をするもとになります。
  • フォーク元へ PR は送りません。

フォークの PR の送り先: GitHub のフォークでは、PR 作成画面や gh pr create の既定の送り先がフォーク元になります。万一 PR を作るときは、base repository が自分のリポジトリになっているか確かめてください。

ブランチ

ブランチ用途

feature/…機能の追加
fix/…不具合の修正

docs/…資料・AI 用の設定（skills やサブエージェント）

取り込みとタグ

実機で確かめてから、--no-ff で main に取り込みます。ブランチ単位の変更が履歴の上で 1 つのまとまりとして残ります。

ファームウェアを書き込んだら、main のそのコミットに fw-日付 の注釈付きタグを打ちます。メッセージには書き込んだターゲットを書きます。同じ日に 2 回目を打つときは fw-2026-10-11.2 のように番号を付けます。

git switch main
git merge --no-ff feature/<名前>
git tag -a fw-2026-10-11 -m "R: sosho_R_trackpad / L: sosho_L_trackpad"

タグは取り込みを確かめてから打つ: 取り込みとタグは別々のコマンドで実行し、タグを打つ前に git log -1 --oneline で main の先頭が取り込みのコミットになっていることを確かめます。取り込みのメッセージは 変更履歴 に載るので、長いときはファイルに書いて git merge --no-ff -F <ファイル> <ブランチ> で渡します（git merge は -F - で標準入力を読めません）。違うコミットに打ってしまったら、push する前に git tag -d <タグ> で消して打ち直します。

前の版に戻す

書き込んだ版にはタグがあるので、そこからビルドし直せば戻せます。

git tag -l 'fw-*'
git switch --detach fw-2026-10-01
./scripts/build-local.sh sosho_R_trackpad
git switch main

バックアップ（push）

push は自分の手で、ときどき行います。Claude からの git push は .claude/settings.json で禁止してあります（意図的な設定です）。

git push origin main --tags

GitHub Actions

ビルドはローカルに一本化し、GitHub Actions は使いません。.github/workflows/build.yml は本家由来のファイルとして残し、GitHub のリポジトリ設定（Settings → Actions → General → Disable actions）で止めます。ファイルを残しておけば、Docker が使えないときに設定を戻すだけで予備のビルド手段になります。

コミットメッセージ

日本語で書きます。1 行目に何をしたかの要約、空行を挟んで理由や補足を書きます。本家由来の古い履歴は英語ですが、このリポジトリでの変更は日本語に統一します。

ビルド

所要時間

Apple Silicon、Docker に 8 CPU・メモリ 4.1GB を割り当てたときの実測です。

ケース所要時間
初回（イメージ取得・west update・フルビルド）約 6 分
キーマップを変えて 1 ターゲット約 14 秒
何も変えずに 1 ターゲット約 6 秒
--all（5 ターゲット、キャッシュあり）約 60 秒

試行錯誤の間は 1 ターゲットだけをビルドし、--all はまとめて書き込むときに使います。

仕組み

  • ビルドは Docker イメージ zmkfirmware/zmk-build-arm:stable の中で動きます。
  • west ワークスペース（ZMK 本体と依存一式）と ccache は、名前付きボリューム sosho-zmk-ws に置きます。初回に取得したものを以降ずっと再利用します。
  • このリポジトリ自身も Zephyr のモジュールです。zephyr/module.yml が board_root（シールドの場所）に加えて、独自のコードの cmake（CMakeLists.txt・src/）と kconfig（Kconfig）を供給します。
  • ディスク使用量はイメージ 2.2GB とワークスペース 3.2GB です。捨てるときは docker volume rm sosho-zmk-ws。
  • ZMK や外部モジュールの版は、config/west.yml で動作を確かめたコミットに固定しています。--update しても固定した版を取り直すだけで、版は動きません。

ZMK の版を上げる

ZMK 本体や外部モジュールの修正を取り込みたいときの手順です。版を上げるとビルドが壊れたり挙動が変わったりすることがあるので、専用のブランチで試し、実機で確かめてから固定し直します。左右は必ず同じ版にそろえます。

zmk-rgbled-widget を上げるとき: src/charging_led.c が widget の内部（src/widget.c の大域変数 led_msgq・led_layer_color・led_current_color と struct blink_item の並び）に頼っています。これらが変わっていないか確かめます（ハードウェア › 電池と充電）。

  1. ブランチを切る。 git switch -c build/update-zmk main

  2. 上げたいものの revision を書き換える。 config/west.yml の該当プロジェクトを main（最新）か、タグ・新しいコミットにします。

  3. 取得する。 ./scripts/build-local.sh --update。調査用コピー（.zmk-ref/）も新しい版で作り直されます。

  4. 何が変わったかを見る。 新旧の .zmk-ref/VERSIONS.txt を比べ、ZMK の変更履歴を読みます（AI に頼めば要点をまとめます）。

  5. ビルドして、左右とも書き込んで確かめる。 左右のつながりがおかしくなったら 接続がおかしいとき の手順で直します。

  6. 固定し直す。 問題が無ければ、.zmk-ref/VERSIONS.txt に記録されたコミットで config/west.yml の revision を固定し、コミットして main に取り込み、タグを打ちます。

書き込み

  1. ブートローダに入れる。 XIAO のリセットボタンを素早く 2 回押すと、USB ドライブとして見えます。

  2. uf2 をコピーする。 firmware/<ターゲット>.uf2 をそのドライブにコピーします。Finder でのコピーがうまくいかないときは、ターミナルでコピーします（ドライブ名は ls /Volumes で確かめる）。

    cp -X firmware/sosho_R_trackpad.uf2 /Volumes/<ドライブ名>/

  3. 再起動を待つ。 書き込みが終わると自動で再起動します。このときドライブが急に消えるので、macOS が「取り外された」と警告しますが、正常な動きです。

左右で別の uf2 です。 sosho_L_* は左、sosho_R_* は右に書き込みます。トラックパッド版とトラックボール版も取り違えないでください。この機体の組み合わせは 右 sosho_R_trackpad ／ 左 sosho_L_trackball です。

何を変えたかによって、書き込む側が変わります。

変えたもの書き込む側
キーマップ・コンボ・エンコーダの割り当て右だけ（キーマップはセントラルが処理する）
ポインタの速度・反転（左右とも）右だけ（input-processors は右の overlay にある）
右の *.conf・*.overlay右
左の *.conf・*.overlay左
共通の sosho.dtsi、config/west.yml左右とも

PC とつながらないとき

右（セントラル）の LED が、起動時の電池残量の表示のあとに 1 回、PC との接続状態を点滅で示します。接続先を切り替えたときも同じように示します（色の意味は zmk-rgbled-widget の説明による）。

色状態対処
🔵 青つながっているUSB ケーブルが刺さっていると入力は USB 側に出る。ケーブルを抜くか、&out OUT_BLE で Bluetooth 出力に切り替える
🟡 黄いまの接続先にペアリング情報が無い（新しい接続を待っている）下の手順の 1 → 3
🔴 赤ペアリング情報はあるのに、つながっていない（PC 側と記録が食い違っている）下の手順の 1 → 2 → 3

  1. PC 側の登録を消す。 macOS ならシステム設定 → Bluetooth で sosho の ⓘ から「このデバイスの登録を解除」。

  2. キーボード側の記録を消す。 接続先を選んでから（&bt BT_SEL 0〜4）、&bt BT_CLR を押します。LED が黄になります。ファイルの初期値のキーマップでは、どちらもレイヤー 3（右手の最下段、右から 2 番目の MO3 を押しているあいだ）にあり、接続先 0〜4 は U・I・O・P・BS の位置、BT_CLR は右手の右下の Shift の位置です。

  3. PC からつなぐ。 Bluetooth 設定の「近くのデバイス」に出てくる sosho を接続します。

ファームウェアの書き込みでは、ふつうペアリング情報は消えません。それでも 2026-10-11 に右を書き込んだあと、PC とつながらなくなり、上の手順でつなぎ直しました（原因は未確認）。

接続がおかしいとき

左右が繋がらない、ペアリングがおかしいといったときは、設定を消してから書き直します（ZMK 公式の手順）。

  1. 左右とも settings_reset.uf2 を書き込む。

  2. 左右とも通常の uf2 を書き直す。

  3. 左右が繋がらなければ、両方のリセットボタンをほぼ同時に押す。

  4. PC の Bluetooth 設定から古い sosho を削除して、ペアリングし直す。

Docker がどうしても使えないときは、GitHub Actions を有効に戻してブランチを push し、Actions のページから成果物をダウンロードできます。

ビルドスクリプトを直すとき

scripts/build-local.sh と scripts/build-in-container.sh には、壊すとビルドが通らなくなる前提があります。

  • west ワークスペースをリポジトリ直下に置かない。 west init -l config は topdir をリポジトリルートにするため、west update が作る zephyr/ が既存の zephyr/module.yml と衝突します。この module.yml が board_root: . と独自コードの cmake・kconfig を供給しており、失うと boards/ と src/ が見つからなくなります。ZMK 公式 CI も同じ回避をしています。シンボリックリンクも不可です（west init -l は Path.resolve() するのでリポジトリ内に戻ってしまう）。
  • -u $(id -u) を付けない。 Zephyr SDK は root の CMake パッケージレジストリ（/root/.cmake/packages/Zephyr-sdk）に登録されています。同じ理由で /root に何もマウントしないこと。
  • ビルドディレクトリは名前付きボリュームに置く。 macOS の bind mount は小さなファイルが大量にあると極端に遅くなります。
  • west zephyr-export を毎回実行する。 --rm で /root が消えるためです。
  • 複数語の shield は、1 つの空白区切り文字列として -DSHIELD に渡す。 フラグを分けてはいけません（Kconfig.shield の shields_list_contains がこのリストを解釈します）。
  • snippet は west の引数なので -- より前、cmake-args は -- より後に置きます。

資料の更新

資料は docs/ の HTML です。docs/index.html をブラウザで開いて読みます。外部への依存は無いので、ファイルを直接開けば表示できます。左のナビの「資料を検索」（または入力欄の外で /）で、全ページをキーワードで探せます。スペースで区切ると、すべての語を含む節に絞り込みます。

AI と進めるとき

Claude Code は毎回 CLAUDE.md を読み込み、そこから資料や skills をたどります。作業の型が決まっているものは skills やサブエージェントにして、手順と前提を書き込んであります。頼み方は普段どおりで構いません。たとえば「左のトラックボールを少し遅くしたい」と頼めば、/add-feature の流れで調査・編集・ビルド・レビューまで進み、書き込みの手前で止まります。

skills とサブエージェント

  • /add-feature skill opus メイン会話で実行

    双掌 (sosho) のファームウェアに機能を足す・設定を変える・不具合を直すときの一連の流れ（要否の判断 → 調査 → ブランチ → 編集 → lint・資料・ビルド → レビュー → コミット → 実機確認の依頼）。コンボ、behavior、マクロ、エンコーダの挙動、ポインタの速さや向き、Kconfig、外部モジュールの追加・変更を頼まれたら、作業を始める前にこれを使うこと。キー割り当てだけの変更なら ZMK Studio で済むので使わない。

  • /retro skill opus メイン会話で実行

    skills・サブエージェント・CLAUDE.md の改善案を出す振り返り。.claude/improvements.md の未対応メモと、このセッションで手順どおりに進まなかった出来事から「どのファイルをどう直すか」を提案し、ユーザーが承認したものだけを適用する。作業の区切りでフック（retro-nudge）から促されたとき、またはユーザーが振り返り・改善提案・skills の見直しを頼んだときに使う。

  • /update-docs skill sonnet メイン会話で実行

    双掌 (sosho) の資料（docs/*.html）を書く・直すときの決まりごと。ページのひな形、使える CSS の部品、自動生成ブロックの扱い、生成器（scripts/docgen/）の足し方、文章の書き方、矛盾の確かめ方、見た目の確かめ方。資料のページを足すとき、手書きの説明を直すとき、資料に新しい事実を載せるとき、生成器を足すときは、HTML を書き始める前に必ずこれを読むこと。

  • /zmk-build skill haiku fork で実行

    双掌 (sosho) のファームウェアを lint してビルドし、結果を要約して返す。キーマップ・コンボ・エンコーダ挙動・ポインタ設定・Kconfig を変更した後の検証に使う。引数はターゲット名（複数可。省略時は sosho_R_trackpad、--all で全部）。書き込みはユーザーが行う。

  • config-reviewer サブエージェント sonnet effort: medium

    双掌 (sosho) の設定変更（キーマップ・シールドの dtsi / overlay / conf・build.yaml・west.yml）を、コミットや書き込みの前にレビューする。lint と資料の生成チェックを実行し、ZMK の書き方の誤り、左右の書き込み先、既知の課題への抵触、資料の更新漏れや記述どうしの矛盾を指摘する。設定ファイルを変更したら、コミットする前に必ずこのエージェントに見せること。指摘だけを返し、ファイルは直さない。

  • docs-sync サブエージェント sonnet effort: medium

    設定やスクリプトを変えたあとに、docs/ の資料（HTML）を実態に合わせる。scripts/gen-docs.py で生成部分を作り直し、手書き部分の古くなった記述や、ほかの記述との矛盾を直して、何を直したかを報告する。設定やスクリプトを変えて手書きの説明が古くなりそうなときや、資料の点検を頼まれたときに使う。

  • zmk-researcher サブエージェント sonnet effort: medium

    ZMK 本体・外部モジュール（zmk-rgbled-widget / zmk-pmw3610-driver / zmk_encoder / zmk-input-processor-report-rate-limit）・XIAO のボード定義の仕様を、このリポジトリが実際に使っている版のソースとドキュメントで調べて答える。「ZMK で○○はできるか」「この behavior・Kconfig・devicetree プロパティの意味と書き方」「この挙動はどこで実装されているか」を確かめたいときは、記憶で答えずにこのエージェントに調べさせること。読み取り専用。

使いながら直す仕組み

skills やサブエージェントは、使って困ったところを直すことで良くなっていきます。困ったことは作業中にメモしておき、作業の区切りで Claude が改善案を出します。直すかどうかを決めるのは自分です。

  1. メモする。 手順どおりに進まなかったことを、Claude が .claude/improvements.md に 1 行ずつ書きます。

  2. 区切りで提案する。 何かを仕上げてコミットした直後（直近 30 分以内にコミットがあり、未コミットの変更が無いとき）に未対応のメモがあると、ターンの終わりに Stop フックが働き、Claude が /retro の手順で改善案を出します（1 セッション 1 回まで）。自分から /retro と頼むこともできます。

  3. 選んで直す。 適用する案を番号で選ぶと、その分だけ直して、メモを「対応済み」に移します。

  • skills・サブエージェントが手順どおりに進まなかったとき（失敗、前提の不足、遠回り、ユーザーからの訂正、モデルの力不足や過剰）は、その場で .claude/improvements.md の「未対応」に 1 行書く。直すのは後でよい
  • メモを書いたら python3 scripts/gen-docs.py も実行する（資料の改善メモ一覧がこのファイルから作られ、放っておくと --check が落ちるため）
  • サブエージェントや fork の skill の報告に「改善メモ」があれば、メイン会話がそれを転記する
  • 作業の区切り（直近 30 分以内にコミットがあり、未コミットの変更が無い）で未対応のメモがあると、Stop フック（.claude/hooks/retro-nudge.py）が /retro での改善提案を促す。1 セッション 1 回まで。止めたいときは環境変数 SOSHO_RETRO_NUDGE=0
  • 改善案を適用するのは、ユーザーが承認したものだけ
